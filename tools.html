Tool、MCP、Skill 比較

    

      

        
本質解決什麼上下文成本例子

        
          
Tool有名稱、說明、參數 schema 的函式；由本機 Agent 負責執行讓模型能「動手」：讀檔、跑指令、改檔每個工具的定義每一輪都送，約百餘到數百 token／個Read、Bash、Edit

          
MCP工具的標準接口（JSON-RPC）；工具由獨立的 server 提供，Agent 是 client不必為每個 Agent 重寫整合，直接接公司系統和一般工具相同：定義每輪都送；對模型來說它就是工具mcp__tfs__wi_list

          
Skill一個資料夾，核心是 SKILL.md（做事流程與腳本）；用到才載入教模型「怎麼做」一件事，不必每次都貼流程平常只佔名稱加一句描述；被呼叫後全文才進 context（數千 token）code-review、deploy

        
      

    

  






  

    
怎麼知道它們什麼時候被呼叫？
三種都是模型自己判斷要不要用

    

      

        
什麼時候載入什麼時候呼叫誰決定

        
          
Tool每一輪都在（工具定義常駐上下文）模型判斷「這件事需要動手」，例如讀檔、跑指令模型，看工具的 description

          
MCP啟動 session 時連到 MCP server，取得工具清單（只做一次）跟 Tool 一樣；名稱像 mcp__tfs__wi_list模型

          
Skill啟動時只載入名稱和一句描述① 模型判斷任務符合描述，呼叫 Skill 工具載入全文 ② 你自己打 /skill名稱模型或你

        
      

      
模型只會「要求」呼叫，真正執行的是你電腦上的 Agent（例如 Claude Code）。


      

        
在 Claude Code 怎麼看看到什麼

        
          
對話畫面本身每次呼叫都會顯示一行，例如 ● Bash(git status)、● tfs - wi_list (MCP)、● Skill(code-review)

          
Ctrl + O展開詳細內容：送了什麼參數、回了什麼結果

          
/mcp連了哪些 MCP server、連線狀態、各自提供哪些工具

          
/context上下文裡各部分佔多少 token：系統工具、MCP 工具、Skill 描述、CLAUDE.md、對話

          
Hooks（PreToolUse）每次呼叫工具前自動執行，可以記錄或攔截；matcher 設 mcp__.* 就能記下所有 MCP 呼叫

          
直接用 API回應的 stop_reason 是 "tool_use"，content 裡有 tool_use 區塊

        
      


      
想讓它一定被呼叫：把 description 寫清楚（模型靠它選工具）；直接說「用 tfs 工具查」；Skill 可以直接打 /code-review；用不到的 MCP 先關掉，工具太多比較容易選錯，也浪費 token。

    

  






  

    
看完要記得

    
    
      
  • 模型只輸出結構化的呼叫要求（stop_reason: "tool_use"），真正執行的是你電腦上的 Agent；結果再用 tool_result 送回去。
    • 
      
  • description 寫得好壞，決定模型選對工具：模型只看得到名稱、說明和參數 schema。
    • 
      
  • MCP 對模型來說就是工具：只是多了一層標準協定，改名成 mcp__server__tool 後塞進同一個 tools 陣列。
    • 
      
  • Skill 平常只佔一句描述（漸進揭露）；被用到時全文才注入，之後每一輪都要重送。
