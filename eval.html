LLM 評測實驗

情境：你改了客服知識庫 agent 的 prompt，想知道新版能不能上線。左邊決定測試集、每題跑幾次和要看哪些指標，右邊比較舊版 A 與新版 B：每次的回答、命中的事實、亂編的句子、工具呼叫，以及能不能上線的判斷。

        規則檢查 vs LLM 當裁判（LLM-as-judge）：工具名稱對不對、格式、長度可以用程式直接判，快、便宜、結果固定。「有沒有亂編」「事實有沒有答到」要看語意，才交給另一個模型當裁判，它能處理換句話說，但會有偏差、結果也不一定穩定。所以裁判本身也要驗：拿一批人工標註過的答案給它評，一致率夠高才能信。
      

    

  






  

    
看完要記得

    
    
      
  • 固定測試集。每次改 prompt 或換模型，都用同一批題目跑，分數才能前後比較。
    • 
      
  • 多跑幾次看穩定度。同一題跑 1 次可能剛好答對；跑多次才看得出會不會偶爾失手，一致性低本身就是問題。
    • 
      
  • 指標要能量化。把「好不好」拆成可以算分的項目：有沒有亂編、事實涵蓋率、工具有沒有呼叫對、格式、長度。
    • 
      
  • 版本比較抓回歸。新版平均分數更高，不代表每一題都更好；重要題目一旦退步，就算整體進步也不能直接上線。
    • 
      
  • 真實失敗案例回填成測試。線上出現的錯誤，修好之後補進測試集，避免同樣的錯誤再次發生。
    • 
    

  





口試怎麼答（約 30 秒）
評測就是用一組固定的測試題，每次改 prompt 或換模型都重跑，用量化指標判斷有沒有變好。我會把指標拆成有沒有亂編、關鍵事實涵蓋率、工具呼叫是否正確、格式和長度，每題跑多次看穩定度，再拿新舊版本逐題比較。重點是看回歸：新版平均分數高，但如果某個重要題目退步，就不能上線。上線前先定好門檻，例如不亂編率要到 95% 以上，而且關鍵題目不能退步。
  • 被追問時可以補：能用程式判斷的就用規則檢查，例如工具名稱、JSON 格式、長度；需要語意判斷的才用 LLM 當裁判。
  • 被追問時可以補：LLM 裁判本身有偏差，要拿人工標註的樣本校準它，確認一致率夠高，也要定期抽查。
  • 被追問時可以補：線上抓到的真實失敗案例要補進測試集，測試集才會越來越貼近真實使用。
  • 被追問時可以補：評測本身也要花錢，所以測試集要精選、分層，重要題目多跑幾次，一般題目少跑。
